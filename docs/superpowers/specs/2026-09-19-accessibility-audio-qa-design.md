# 화면–음성 접근성 QA: 3분 시연과 MVP 설계

작성: 2026-09-19. 상태: 사용자가 1시간 구현 목표에 따라 기본 검사를 4–5개로 줄이는 범위 조정을 지시했다. 기본 검사 5개와 음성·이미지 의미 검사를 현재 범위로 확정한다. 실행은 리드 주도의 Git 병렬 협업으로 변경되었다. 최신 소유권·계약은 구현 계획의 Git 협업 실행 계약을 따른다.

최신 착수 조건: 사용자 지시에 따라 제품·테스트·샘플 코드는 2026-09-19 14:00 KST부터 새로 작성한다. 이전 실험은 사전 연구로 구분한다. 계정·환경·스폰서 준비 상태와 개발 시간표는 기존 구현 계획의 ‘실행 환경과 사전 확인’ 절에서 관리한다.

사용자 현장 확인 반영: Daytona는 필수, 다른 스폰서는 선택 가산점이다. Nosana 추가 크레딧은 지급되지 않을 것으로 예상하며, 팀원 키는 아직 확보되지 않은 대안이다. 발표에는 PDF도 사용할 수 있으며, 사용자 최신 정정에 따라 장수 제한 없이 필요한 내용만 보여준다. 최신 기능 범위는 아래 혼합 검사 구조를 따른다.

## 목적과 성공 조건

키오스크 웹앱 개발자가 화면의 중요한 안내가 실제 출력 음성에도 전달되는지 확인하는 반복 QA를 자동화한다. 해커톤에서는 결제 실패 후 재시도 안내가 음성에서 빠지는 사례 하나에 집중한다.

사용자가 확정한 조건은 3분 시연, 기존 axe AI 제품과 설명 가능한 차별점, 실제 문제 해결, 완성된 최소 기능, Daytona의 실제 활용이다. 실제 장애인의 경험 재현과 사람처럼 지연을 넣는 방식은 기각된 범위로 유지한다.

완료 조건은 HTML 기반 샘플 실행 → 규칙 검사 및 증거 수집 → 필요한 의미 검사만 AI 호출 → 검사 종류별 결과 확인 → 안내 수정 → 같은 검사 재실행이 연결되는 것이다. 음성과 이미지 설명의 정상·결함 사례를 실제 모델로 확인하며, 규칙 검사만 실행할 때는 모델 호출이 없어야 한다.

## 최신 프로젝트 구조: 규칙 검사와 AI 검사 분리

사용자 요청: HTML에서 규칙으로 확인 가능한 접근성 항목은 AI 없이 검사하고, 음성 안내와 이미지 대체 텍스트의 의미 적합성처럼 문맥이 필요한 작업만 AI에게 맡긴다. 실행 순서와 검사 대상 선택은 일반 코드가 결정한다. AI가 모든 도구를 선택하는 범용 에이전트 구조는 만들지 않는다.

### 선택한 방식

- 채택: Daytona 브라우저에 HTML·CSS·스크립트를 로딩하고, DOM과 계산된 스타일에서 아래 5가지 기본 항목을 직접 검사한다. 같은 실행에서 수집한 이미지·화면·녹음으로 선택한 AI 검사만 실행한다.
- 사용자 요청으로 제외: axe-core 및 Deque 제품 의존성. 기존 도구의 검사 항목을 참고해 좁은 자체 규칙을 구현하며, 외부 엔진을 호출하거나 종합 접근성 엔진을 재구현하지 않는다.
- 제외: 원본 HTML 문자열만 검사. CSS 적용 결과와 자바스크립트 이후 화면을 반영하기 위해 브라우저의 DOM·계산된 스타일을 사용한다.
- 제외: AI에게 페이지 전체를 주고 모든 항목을 판정. 명확한 규칙까지 모델 비용·변동성에 노출된다.

첫 입력은 기존 시연용 HTML과 로컬 자산 묶음이다. 검사 모듈은 Playwright 페이지를 받아 동작한다. 파일 업로드 화면, 임의 사이트 탐색·로그인·크롤링은 이번 구조 변경에 포함하지 않는다.

### 책임 분리

| 검사 경로 | 입력 | 맡길 작업 | 결과의 한계 |
|---|---|---|---|
| 규칙 검사 / AI 호출 없음 | 렌더링된 DOM·계산된 스타일 | 대체 텍스트 유무, 단색 대비, 폼 레이블, 버튼 이름, CSS 글자 크기 | 기본 항목의 관찰 결과다. 복잡한 배경은 확인 필요, 글자 크기 권장은 별도 표시하며 전체 접근성 통과로 확대하지 않는다. |
| 음성 의미 검사 / AI | 최종 화면, 실제 출력 녹음의 전사, 관찰 시간 | 결제 결과와 다음 행동의 누락·모순·전달 여부 | 녹음·전사 실패는 실행 오류, 모호한 의미는 수동 확인. |
| 대체 텍스트 의미 검사 / AI | 이미지 캡처, alt와 ARIA 이름 정보, 가까운 문맥 | 이미지의 목적에 맞는 설명인지, 필요한 정보가 빠졌는지, 빈 alt가 장식 용도로 적절한지 | 이미지가 없거나 보이지 않으면 판정하지 않는다. 문맥이 부족하면 수동 확인. |

### 공식 도구 조사와 선정 근거

2026-09-19에 [WAVE 공식 API 문서](https://wave.webaim.org/api/details), [Lighthouse 공식 접근성 검사 목록](https://developer.chrome.com/docs/lighthouse/accessibility/scoring), [HTML_CodeSniffer 공식 WCAG 검사 목록](https://squizlabs.github.io/HTML_CodeSniffer/Standards/WCAG2/)을 확인했다. 기능과 판정 근거를 참고하며 이들의 검사 엔진은 사용하지 않는다.

[WebAIM Million 2026](https://webaim.org/projects/million/)은 100만 홈페이지에서 WAVE가 자동 검출한 오류의 96%가 낮은 대비, 이미지 대안 누락, 폼 레이블 누락, 빈 링크, 빈 버튼, 문서 언어 누락의 여섯 범주였다고 보고한다. 이 값은 기능 우선순위의 근거이며, 우리 자체 검사기의 탐지율·전체 접근성 보장 비율이 아니다. 1시간 구현 목표에 따라 이 중 키오스크 흐름에 우선 필요한 대비·이미지 대안·폼 레이블·버튼 이름을 선택한다. 글자 크기는 사용자 요청을 반영한 별도의 가독성 주의 항목이다. 링크 이름·문서 언어·문서 제목은 조사했지만 이번 구현에서 제외한다.

| 우선 구현 항목 | 참고한 실제 도구 기능 | 우리 MVP에서 확인할 것 |
|---|---|---|
| 이미지 텍스트 대안 | WAVE alt_missing, Lighthouse image-alt | alt와 유효한 ARIA 이름의 유무. 빈 alt는 의미 확인 대상으로 분리 |
| 텍스트 대비 | WAVE contrast, Lighthouse color-contrast | 확정 가능한 단색의 상대 휘도 대비. 계산 불가능한 배경은 보류 |
| 폼 레이블 | WAVE label_missing, Lighthouse label | input·select·textarea의 연결된 label 또는 대체 이름 유무 |
| 버튼 이름 | WAVE button_empty, Lighthouse button-name | 버튼이 전달하는 접근 가능한 이름의 유무 |
| 글자 크기 주의 | 사용자 요청; WCAG 위반 규칙으로 취급하지 않음 | CSS font-size 수집, 제품 권장값 16px 미만 주의 |

제목 단계·테이블 헤더·ARIA 역할 전체 검증·키보드 탐색·깜박임·동영상 자막은 이번 기본 검사에 추가하지 않는다. 이름이 있는지와 그 이름이 적절한지는 구분한다.

자체 규칙의 정확한 범위:

1. **텍스트 대안 유무:** 보이는 img의 alt 속성 누락·빈 값·비어 있지 않은 값을 구분한다. alt가 없어도 유효한 aria-label 또는 aria-labelledby가 있으면 텍스트 대안이 전혀 없다고 단정하지 않는다. title만 있는 이미지는 이름 전체 누락과 구분해 주의로 남긴다. alt도 다른 이름 근거도 없는 일반 이미지는 누락으로 보고한다. 빈 alt, presentation 역할, aria-hidden처럼 장식 의도를 나타내는 경우는 문맥 확인 대상으로 남긴다. 유무 통과는 설명 의미의 적합성을 뜻하지 않는다.
2. **명도 대비:** 일반 흐름에서 불투명한 단색 전경과 배경을 확정할 수 있는 텍스트만 상대 휘도로 계산한다. 투명한 배경은 조상에서 불투명 단색을 찾되 끝까지 찾지 못하면 보류한다. 일반 텍스트는 4.5:1, 큰 텍스트는 3:1을 적용한다. 첫 큰 텍스트 분류는 CSS 24px 이상 또는 굵기 700 이상이면서 18.667px 이상이며, 측정한 크기·굵기·색·대비·기준을 결과에 남긴다. 반올림 전 값으로 비교한다. 이미지·그라데이션 배경, 반투명 전경·opacity, 필터·블렌딩·텍스트 그림자·변형·중첩 배경처럼 단순 계산이 부정확한 경우는 확인 필요다. 비활성·비가시 요소는 계산 대상에서 제외한다. 로고·장식 여부의 문맥 판단은 이 규칙으로 확정하지 않는다.
3. **텍스트 크기:** 계산된 font-size를 CSS px로 수집한다. 16px 미만은 제품의 가독성 권장값에 따른 주의 대상으로 표시한다. 16px을 WCAG 또는 국내 법정 최소값으로 설명하지 않으며, 그 이상도 접근성 통과로 표시하지 않는다. 물리적 글자 높이(mm)와 동일하게 취급하지 않는다. 200% 확대 후 사용성 검사는 별도 범위이며 이번 규칙에 포함하지 않는다.
4. **폼 레이블:** 숨겨진 입력을 제외한 native input·select·textarea에서 연결된 label, aria-label, 유효한 aria-labelledby 등 이름 근거를 확인한다. placeholder만으로 레이블이 있다고 처리하지 않는다. title만 있는 경우는 완전한 이름 누락과 구분해 주의로 남긴다. 버튼형 input은 버튼 이름 검사로 보낸다.
5. **버튼 이름:** 이름을 innerText만으로 판정하지 않는다. ARIA 이름, 이미지 대안, title, native 버튼의 value 등 이름 근거를 함께 본다. 가능한 경우 Chromium의 접근성 트리에서 계산된 이름으로 확인한다. 복잡한 이름 계산을 확정하지 못하면 실패를 단정하지 않고 확인 필요로 남긴다. 이번에는 버튼만 검사하고 링크 이름 검사는 제외한다.

대비 기준의 출처: [W3C WCAG 2.2 대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). 텍스트 크기 권장값과 구분할 확대 기준: [W3C 텍스트 크기 조절](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html). 이 기본 대비 검사는 웹 기준을 참고한 개발용 검사이며 국내 무인정보단말기 기준 전체의 적합 판정이 아니다.

### 실행 흐름

1. 일반 코드가 선택한 검사 목록(rules, audio, alt_text)을 검증한다. 기본은 세 검사이며, 규칙 검사만 실행하는 경로도 제공한다.
2. Daytona에서 샘플을 로딩하고 정해진 결제 흐름을 실행한다. 검사는 실제 로딩된 화면 상태를 대상으로 한다.
3. 해당 상태의 DOM·계산된 스타일을 수집해 5가지 기본 항목을 실행하고 관찰값과 판정 근거를 보존한다. AI 작업의 성공·실패와 독립적으로 이 결과를 보고한다.
4. 음성 검사를 선택했을 때만 녹음·전사·음성 의미 판정을 수행한다. 규칙 검사만 선택하면 음성 생성 준비와 전사도 하지 않는다.
5. 대체 텍스트 검사를 선택했을 때만 보이는 img 요소의 캡처와 설명·문맥을 수집한다. 요소별 명확한 텍스트 대안 누락을 규칙 엔진이 이미 발견했다면 동일 문제를 다시 AI로 묻지 않는다. 그 외 후보는 AI가 의미를 검토한다.
6. 검사별 결과와 실제 모델 제공자·시간·실행 ID를 저장한다. AI가 규칙 검사 결과를 덮어쓰지 않는다. 샘플 상태 이름과 정답은 AI에 전달하지 않는다.

이미지 검사 첫 범위는 보이는 img 요소 최대 3개다. 한도를 넘는 이미지는 미검사로 명시한다. 샘플에는 1개를 둔다. CSS 배경 이미지, 복잡한 iframe·shadow DOM 탐색은 추가하지 않는다. 빈 alt는 일괄 통과나 일괄 실패로 처리하지 않고 이미지의 역할과 문맥을 함께 본다. 대체 텍스트 의미 검사를 규칙의 확인 필요 목록에만 한정하지 않는다. 설명이 존재해도 그 의미는 틀릴 수 있기 때문이다.

AI API 오류가 나도 완료된 규칙 결과와 수집한 증거는 유지한다. 결과는 규칙 검사·음성 검사·이미지 설명 검사로 나누고, 각 경로의 완료·오류·미실행 상태를 표시한다. 전체 접근성 점수나 하나의 녹색 통과 표시로 합치지 않는다.

### 파일 구성

```text
daytona/
  app.py                 HTTP 요청, 한 번에 한 실행, 수정·재검사
  runner.py              Daytona 생성·작업 실행·파일 수집·정리
  worker.py              정해진 브라우저 동작과 검사 분기
  rules.py               5가지 기본 항목의 자체 검사; 모델 API 의존 없음
  audit.py               음성·대체 텍스트 판정 함수와 응답 검증
  sample/                결제 HTML, 이미지·음성 등 샘플 자산
  static/                단일 결과 화면 HTML·CSS·JavaScript
  tests/                 규칙·선택적 AI 호출·오류·재검사 검증
  .runtime/runs/         실행별 규칙 원본·화면·이미지·녹음·판정
```

기존 파일 역할을 유지하고 rules.py만 검사 모듈로 추가한다. audit.py에는 기존 음성 판정과 별개의 이미지 설명 판정 함수를 둔다. 두 함수는 필요할 때만 호출하며, 공통 모델 요청과 응답 검증 정도만 공유한다. 별도 에이전트 서버, 작업 큐 서비스, 플러그인 등록 구조, LangGraph 같은 프레임워크는 필요하지 않다.

### 구조 검증의 합격 조건

- 모델 키 없이 규칙 검사만 실행해 명확한 HTML 결함을 찾는다. 모델 호출 수는 0이다.
- 규칙 오류가 있는 요소는 근거·선택자와 함께 보고한다. 불확실한 규칙 결과를 통과로 바꾸지 않는다.
- 대비 계산은 검정/흰색 21:1, 같은 색 1:1, 4.5 경계와 큰 글자 3:1 기준으로 검증한다. 그라데이션·투명 배경을 확인할 수 없는 경우는 보류한다.
- alt 누락, 유효한 ARIA 이름, 빈 alt를 구분한다. 16px 미만 안내는 제품 권장값임을 표시한다.
- 연결된 label, ARIA 이름, 이미지로 이름을 가진 버튼을 오탐하지 않는다. placeholder만 있는 폼과 이름 없는 버튼을 찾는다.
- alt는 존재하지만 이미지와 뜻이 다른 경우를 AI가 검출하고, 표현이 다른 올바른 설명은 허용한다. 빈 alt를 가진 정보 이미지와 장식 이미지의 차이도 확인한다.
- 음성 누락 발견 → 실제 안내 수정 → 새 녹음의 통과 흐름은 유지한다.
- 모델 오류 또는 특정 AI 검사 미선택 시 규칙 결과는 보존하고 해당 AI 상태를 명시한다.
- 실제 이미지·음성 없이 성공 결과를 만들지 않는다. 샘플 정답·수정 상태가 모델 입력에 섞이지 않는다.

3분 시연의 중심은 기존 음성 누락 수정·재검사다. 규칙 검사와 대체 텍스트 판정은 같은 결과 화면에서 근거와 함께 보여주되 별도의 긴 시연을 추가하지 않는다. 대체 텍스트 AI 판정 자체는 Axe AI와 겹치므로 혁신성의 단독 근거로 삼지 않는다.

## 확인된 기반과 남은 위험

- 실제 Daytona 브라우저에서 재생한 한국어 합성 음성을 PulseAudio 모니터와 FFmpeg로 녹음하고 Whisper API에 전사시키는 실험에 성공했다.
- 성공한 1회 측정: 샌드박스 생성 1.99초, 의존성 설치 13.2초, 재생·녹음 7.84초, 전사 1.54초, 생성부터 삭제까지 37.94초.
- 실제 출력 수집이 검증됐으며, 화면–음성 의미 판정과 아래 시연 전체의 지연·반복 안정성은 아직 검증되지 않았다.
- 가장 큰 남은 위험: AI가 필요한 안내의 누락을 놓치거나, 표현만 다른 정상 안내를 오류로 판단하는 것. 대시보드보다 이 판정부터 구현·검증한다.

## 선택한 접근과 대안

1. 선택: 제공되는 결제 키오스크 샘플과 한 개의 동작 흐름을 실제로 검사한다. 구현·초기화·증거 수집이 단순하고 3분 안에 전후 비교를 전달하기 쉽다.
2. 보류: 임의 URL과 자연어 목표를 받아 사이트 전체를 자율 탐색한다. 로그인·사이트별 흐름·기록 범위가 늘어나 이번 MVP의 안정성을 낮춘다.
3. 제외: 사전 녹화물만 업로드해 분석한다. 분석 기능의 보조 자료로는 가능하지만, 이번 시연의 실제 조작·출력 수집을 대체하지 않는다.

## 샘플 앱과 검사 대상

샘플은 외부 결제망에 연결되지 않는 테스트용 키오스크다. ‘데모용 결제 시나리오’임을 화면에 표시한다. 결제 버튼을 누르면 처리 중 상태를 거쳐 결제 실패 화면으로 전환한다.

- 최종 화면: “결제에 실패했습니다. 다시 시도 버튼을 눌러 주세요.” 및 실제 ‘다시 시도’ 버튼.
- 결함 상태 음성: 처리 중 안내는 나오지만 최종 실패와 재시도 안내는 출력되지 않는다.
- 수정 상태 음성: “결제가 완료되지 않았습니다. 다시 시도 버튼을 눌러 주세요.”처럼 같은 의미를 전달한다.
- 검사 구간: 버튼 조작 전부터 최종 화면이 나타난 뒤 정해진 관찰 구간까지. 첫 MVP에서는 최종 화면 등장 후 최대 8초를 관찰한다. 이는 테스트 조건이며 법적 제한 시간이나 인간의 반응 시간으로 표현하지 않는다.
- 화면과 녹음에는 같은 실행 ID와 상대 시각을 기록한다.

‘수정안 적용’은 허용된 샘플의 최종 음성 안내 설정만 변경한다. 임의 코드 자동 수정 기능으로 표현하지 않는다. 수정으로 테스트 결과를 직접 바꾸지 않으며, 재검사의 화면·녹음·판정이 새 결과를 결정한다.

## 판정 방식

최소 에이전트 흐름은 정해진 결제 동작 실행 → 결과 관찰 → 수집된 증거에 대한 AI 판단이다. 사이트 전체를 자율 탐색한다고 주장하지 않는다.

음성 판정 AI에는 최종 화면 스크린샷, 실제 녹음의 전사문, 관찰 구간, 검사 목적을 제공한다. 대체 텍스트 판정 AI에는 위 구조 절에서 정한 이미지·설명·문맥만 제공한다. 샘플의 결함/수정 상태 이름, 정답 라벨, 음성 생성 원문은 제공하지 않는다.

AI가 확인할 필수 정보는 최종 결제 결과와 화면이 안내하는 다음 행동이다. 표현 차이와 동의어는 허용한다. 출력은 구조화된 다음 세 종류다.

- `pass`: 관찰한 화면의 필수 정보가 음성에도 전달됨.
- `fail`: 누락·모순을 구체적인 화면·음성 근거로 제시할 수 있음.
- `needs_review`: 전사나 의미가 불명확해 판단을 보류해야 함.

실행 실패(`error`)는 위 접근성 판정과 분리한다. 모델 출력 형식 오류, 녹음 실패, API 오류, 타임아웃은 ‘검사 오류’로 표시하며 통과로 만들지 않는다. 정상 안내를 문자열 완전 일치로 판정하지 않는다. AI의 결론과 인용 근거는 실제 결과에서 표시한다.

순수 무음은 수집 장치 장애와 앱의 안내 누락을 이 MVP만으로 구분하기 어려우므로 ‘검사 오류/수동 확인’으로 처리한다. 시연의 결함 상태는 처리 중 음성이 정상적으로 녹음된 뒤 최종 안내가 누락되는 상태다.

## 서비스 화면

화면 하나에 검사 대상·목표, 실행 버튼, 실제 진행 상태, 증거와 판정을 배치한다.

- 상단: 검사 목표와 대상, ‘환경 준비’, ‘검사 실행’, 실제 소요 시간.
- 중앙 왼쪽: Daytona에서 캡처한 화면과 관찰 시점.
- 중앙 오른쪽: 녹음 재생, 실제 전사문, 필수 정보별 누락·전달 상태.
- 하단: 판정 이유, ‘수정안 적용’, ‘다시 검사’, 이전 실행과 현재 실행 비교.
- 상세 실행 정보: 실제 샌드박스 ID, 단계별 시간, 녹음·결과 다운로드.
- 검사 선택: 규칙 검사, 음성 의미 검사, 이미지 설명 검사. 결과는 검사 종류별로 구분하고, AI 오류가 규칙 결과를 숨기지 않게 한다.

진행 상태는 실제 백엔드 이벤트에 맞춰 갱신한다. 가짜 진행률, 미리 정한 AI 답변, 저장된 녹화를 라이브처럼 재생하는 기능은 만들지 않는다. 아직 도착하지 않은 화면은 ‘캡처 대기’로 표시한다. 정상 결과 문구는 ‘이 검사 통과’로 한정한다.

## 최소 구성과 데이터 흐름

현재 작업 폴더 아래 `daytona/`를 제품 코드 위치로 사용한다. 기각된 번역·일기 서비스의 제품 기능은 재사용하지 않는다. 성공한 실험의 Daytona·Playwright·오디오 수집 방식을 제품 코드로 정리해 사용한다.

- 로컬 FastAPI 서버: 화면 제공, 실행 요청, 진행 이벤트, 샘플 수정 설정, 결과 파일 관리.
- 단순 HTML/CSS/JavaScript: 별도 프런트엔드 빌드 도구 없이 단일 검사 화면 구현.
- Daytona 작업자: 샘플 앱 실행, Chromium 조작, 5가지 기본 항목의 자체 검사, 선택된 음성·이미지 증거 수집과 의미 판단 호출.
- 파일 저장: 실행별 JSON·PNG·WAV. 데이터베이스·로그인·멀티테넌트는 추가하지 않는다.
- 동시 실행: 한 번에 한 검사. 중복 요청은 거절하고 기존 실행을 보여준다. 수정은 검사가 끝난 뒤에만 허용한다.

Daytona 샌드박스는 한 시연 세션의 준비와 전후 검사에 재사용하되, 매 검사마다 브라우저 상태와 녹음 파일을 새로 만든다. 완료 후 종료 기능과 짧은 TTL로 정리한다. 키는 서버 환경에서만 읽고 브라우저·증거·로그에 노출하지 않는다. 기존 `.env`의 연결 설정은 값 출력 없이 재사용하며, 실제 키를 소스에 복사하지 않는다.

실제 음성 인식·의미 판단은 모델 API가 담당한다. Daytona 자체에 음성 인식 모델이 내장되어 있다고 표현하지 않는다.

## 차별성 및 범위 표현

발표의 핵심 문장은 “화면의 중요한 안내가 실제 음성 출력에도 전달되는지 검사합니다”다.

무료 axe-core와 유료 Axe AI를 혼동하지 않는다. 이번 MVP에는 유료 Axe AI 직접 실행 비교를 넣지 않는다. 경쟁 제품의 가짜 통과 화면이나 미실행 점수를 표시하지 않는다. 기존 조사에서 공식 자동화 기능으로 확인되지 않은 검사라는 범위로 설명한다.

첨부 국내 키오스크 기준의 필수 시각정보에 대한 청각정보 제공 취지와 연결되지만, 공인 시험·법적 적합성·국내 기준 전체 통과를 판정하지 않는다. 화면에는 필요 시 ‘검증 범위: 최종 상태·다음 행동의 음성 전달’만 명확히 표시한다.

실물 단말기, 이어폰 연결, 높이·버튼 치수, 화면 읽기 프로그램, 모든 장애 유형의 경험 재현, 임의 웹사이트 크롤링, 과금 기능은 이번 MVP에 포함하지 않는다. 이미지 대체 텍스트 검사는 사용자 최신 요청으로 위의 좁은 범위에서 포함한다.

## 구현 우선순위와 검증

1. 의미 판정부터 확인: 동일한 실패 화면에 누락 음성은 `fail`, 표현이 다른 정상 음성은 `pass`, 불명확한 전사는 `needs_review`가 나오는지 실제 모델로 검증한다. 결함 상태 이름과 정답을 모델 입력에서 배제한다.
2. 실제 연결: Daytona 샘플 버튼 조작 → 캡처·녹음 → 전사 → 의미 판정 결과를 실행별로 저장한다.
3. 수정·재검사: 설정을 변경한 뒤 새 녹음·새 판정으로 통과하며, 이전 증거가 덮어쓰이지 않는지 확인한다.
4. 화면 연결: 실제 단계·증거·오류·재검사를 표시하고, 브라우저에서 전체 흐름을 확인한다.
5. 리허설: 실제 결함 검사와 수정 후 검사를 이어서 실행해 시간을 측정한다. 결과를 조작하거나 오류를 숨겨 목표 시간에 맞추지 않는다.

코드 검증은 판정 스키마·오류 분리, 중복 실행 방지, 결과 파일 분리, 수정 후 재검사를 중심으로 한다. 외부 API의 성공을 가짜 SDK 테스트로 대체하지 않는다. 실제 모델·Daytona 검증 횟수와 한계를 최종 결과에 적는다.

## 설계 자체 검토

- 시연 합계는 180초이며 실제 처리 지연은 아직 목표값이다.
- 수정 전후의 화면은 같은 정보를 제공하고 실제 출력 음성이 달라진다.
- ‘음성 파일 생성’과 ‘실제 출력 녹음’을 분리했다.
- ‘접근성 실패’, ‘판단 보류’, ‘실행 오류’를 분리했다.
- 단일 샘플의 검사를 서비스 전체의 접근성 보장으로 확대하지 않는다.
- 우승 가능성·시장 규모·인건비 절감률·유료 Axe 대비 성능 우위는 수치로 주장하지 않는다.
